# Connector subcontracts v1 — platform proposal, UI activation requires B review

This elaborates the frozen v2 connector seam without modifying the shared contract. The engine/UI are not connected yet. Every owner operation uses the existing real account cookie, expected-account and CSRF/Origin protection. Secret values never leave the server except an OAuth authorization URL or a one-time alias/pairing secret explicitly returned to its owner. Callback query strings must be redacted at ingress/application access logs.

- `POST /api/v2/connectors/gmail/connect`: `{capability:'send'|'read'|'send_and_read'}` plus operation key. Returns authorization_url, expires_in. Requested scopes are gmail.send and/or gmail.readonly; no blanket mail.google.com. Fixed configured HTTPS redirect, one-use state bound to account/session, PKCE. Read access requires Google's restricted-scope policy review before public activation.
- `GET /api/v2/connectors/gmail/callback?state=…&code=…`: same verified session, one-use ten-minute state. Tokens encrypted with a dedicated AES-GCM key and account/provider associated data. Returns state/capabilities only.
- `GET /api/v2/connectors/{provider}/status`: configuration and connection state, no credentials.
- `POST /api/v2/connectors/gmail/disconnect`: operation key. Revoke remote grant, erase local credential, cancel queued correspondence. An uncertain revocation is reported, not claimed successful remotely.
- Reviewed sending and bounded reply ingestion will use private jobs and current case-version checks. Sending remains disabled until explicit owner activation and connected acceptance. Provider acceptance tests never send user correspondence automatically.
- `POST /api/v2/connectors/inbound_email/aliases`: `{case_id}` or null with operation key; returns an unpredictable alias token once. Possession permits intake only, never case reads. Delete alias revokes it.
- Inbound adapter contract: verified provider envelope → account-bound immutable original → deduplicated intake. Provider event and original-content IDs are both checked. Unmatched aliases are quarantined/rejected, never assigned by guessed address/email identity. Adapter-specific public webhook routes remain disabled until their real signature scheme and configured provider are accepted. Generic HMAC test fixtures do not prove a real provider works.
- WhatsApp Business webhook can verify Meta's raw-body HMAC and linking before intake. Personal WhatsApp inbox reading is unsupported. Approved template/opt-in/provider account setup remains a separate activation gate.
- Browser extension pairing uses a ten-minute one-use account-bound capability; it does not copy the HttpOnly browser cookie. Audio remains immutable private evidence, with processing provided by B's bounded transcription seam.

Checked 15 November 2026: [Google OAuth web server flow](https://developers.google.com/identity/protocols/oauth2/web-server), [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes), [Gmail MIME sending](https://developers.google.com/workspace/gmail/api/guides/sending), [Gmail push](https://developers.google.com/workspace/gmail/api/guides/push). The present implementation does not provision Pub/Sub or assume its IAM/topic setup. New services, provider costs and public activation require explicit owner decisions.

Implemented adapter elaborations: `POST /gmail/cases/{case_id}/send` accepts the version, exact recipient/subject/body/source IDs, `reviewed:true` and optional `receive_replies:false`. Dispatch requires the separate activation flag; replies use only that reviewed thread for at most 24 polling rounds. `POST /gmail/import` takes message_id and an owned alias token. `POST /extension/pair` takes case_id and returns a ten-minute one-upload capability; `POST /extension/capture` requires `Authorization: Capture …`, with no case-read permission and issuing-session revocation checks. Owner-only intake downloads are `/inbound_email/intake/{id}/content`.

Provider webhook paths are `/inbound_email/resend/webhook` (Svix), and `/whatsapp/webhook` (Meta challenge/raw-body signature). They are disabled without configuration. A WhatsApp batch is split into owner-specific derived JSON records, never disclosed wholesale; these records are not falsely labeled original screenshot/audio bytes. Unsupported media is `manual_attachment_required`. Aliases can be revoked; WhatsApp disconnection removes local links/credentials and pending notifications. Provider-specific setup/live verification remains required. Alias capability values are recoverable by the same authenticated operation replay, not exposed as public case access.
