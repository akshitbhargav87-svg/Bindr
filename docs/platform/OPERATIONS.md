## Schema rollout and rollback

Current platform schema target: **11**. Migrations are additive, transactional and serialized by PostgreSQL advisory lock or SQLite immediate transaction. Existing cases keep ownership; truly ownerless legacy cases become `legacy-unclaimed`. Original references/hashes, sessions, account/complaint drafts remain unchanged. Pre-platform communication dates remain unknown. Historical v2 event ordering ties stay unknown; new events receive causal sequence/version. Job timestamps support dates beyond 2038.

Local development bootstraps automatically. Actual Cloud Run service startup and deployed workers perform a **read-only** revision/table/column check; they refuse a mismatched database. Before any approved rollout, take/verify a Cloud SQL backup, restore it to an isolated database, run `python -m scripts.migrate_platform --upgrade` using an approved migration identity, then `python -m scripts.migrate_platform --check` using the application identity. Validate account/session/source records and original digests before shifting traffic. No production migration was run here.

Rollback has no destructive downgrade command. Additive tables allow the previous app to remain usable, but v2 facts are separate and must not be hidden as if they never existed. Review restore/data-loss consequences and the exact image/schema pairing with the owner before a traffic rollback or database restore. The new Dockerfile/CI configuration has not been built/deployed remotely by this work.

## Worker and retention

`python -m scripts.platform_worker --max-jobs 20` runs a bounded SQL worker batch. SQL leases, stable reminder IDs and bounded retries survive process restart. Timed-out/crashed sends require reconciliation instead of automatic re-send. Deadline revision, fulfillment, archive, opt-out, disconnection, new reply and deletion invalidate dependent work. No public worker/dispatch endpoint exists.

A managed authenticated invocation is still required for Cloud Run scale-to-zero. Prepare a reviewed Cloud Run Job/Scheduler arrangement with service identity, database/private-storage access and the same pinned schema/image. No scheduler or extra cloud service was provisioned. CLI success and SQL durability do not prove unattended cloud delivery. A stale worker cannot commit a cancelled job; external provider acceptance and SQL cannot form one atomic transaction.

Generated exports deny download after 24 hours; physical cleanup runs on worker invocation, so a stopped worker can delay object removal. Case deletion denies v1/v2 access after acceptance, cancels work, then retries known SQL/original/intake/export cleanup. Account deletion additionally revokes sessions, removes contributions/credentials and requests Firebase identity deletion. Cloud backup, GCS soft-delete and ingress/log retention were not independently established. Confirm their actual policies and unknown-object reconciliation before release; downloaded/third-party copies cannot be recalled.
